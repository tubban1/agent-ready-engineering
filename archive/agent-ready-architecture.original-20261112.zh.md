站在系统架构师（System Architect）的视角，**Agent-Ready 的本质绝不是“给系统增加一个 MCP 接口”，也不是“把 API 封装成几个工具”**。

从架构演进的角度来看，Agent-Ready 是一场关于**“调用端假设、状态确定性、资源预算模型与信任边界”**的全面系统重构。架构师可以从以下五个核心维度来透视它：

---

### 维度一：调用端假设的根本颠覆（Client Axiom Shift）

软件架构的第一原则是“定义调用方假设”。在过去几十年中，系统的客户端只有两种：
1. **确定性客户端（代码）**：调用顺序在编译期固定，逻辑是布尔判断，输入输出严格匹配类型；
2. **人类客户端（用户）**：虽然行为随机，但有眼睛、常识和耐心，人脑能在视觉界面中容忍错位、自行拼凑上下文、感知异常并自行兜底。

**Agent-Ready 面临的是第三种全新的客户端——“概率性智能体（Probabilistic Actor）”：**
* 它具备自主规划和语义理解能力，但**完全没有视觉，对隐式上下文零感知**；
* 它的行为是概率性的，会产生幻觉，会在网络抖动时陷入死循环或盲目重试；
* 它的“认知内存”极度受限且极其昂贵（即 Context Window）。

> **架构师的第一思考**：
> **当调用端从“确定性程序”退化为“具备自主决策能力的概率性黑盒”时，我的后端系统如何依然保持状态变更的强确定性与高可靠性？**

### 维度二：把 Context Window 当作系统的“L1 高速缓存”来做容量设计

传统架构师衡量吞吐与资源，看的是 QPS、并发连接数、DB 连接池和 I/O 带宽。
但在 Agent 时代，**上下文窗口（Context Window）就是一种极其昂贵且易被污染的“L1 Cache”，Token 消耗就是新型网络/计算带宽成本。**

* **防缓存污染（Anti-Context Thrashing）**：
  * 如果像传统 API 那样把包含 200 个字段的原始数据倾倒给 Agent，就相当于让海量脏数据冲刷 L1 Cache，导致模型发生注意力稀释（Attention Loss）和幻觉；
* **发现机制的懒加载（Progressive Discovery）**：
  * 架构上必须支持能力的渐进式暴露（如 Bloomroom 的 `get_design_schema` 按需读取），而不是在初始化握手时把所有庞大的 Schema 静态塞进上下文；
* **数据访问层的 Machine-First 重塑**：
  * 传统分页（一次 20 条）对 Agent 来说意味着巨大的多轮 RTT（网络与推理往返）延迟；
  * Agent-Ready 的数据层必须支持**服务端过滤、字段投影（Projection）、游标分片与结构化摘要**，使单次交互的信息密度达到帕累托最优。

### 维度三：非确定性环境下的强状态机与防重试灾难

传统分布式系统依赖 Paxos / Raft 或事务保证一致性。而 Agent 是运行在系统外部的非确定性状态机，极易与服务端产生“状态认知脱节”。

架构师必须在领域模型中注入**防御性可恢复机制（Defensive Resilience）**：

```
                    ┌───────────────────────────┐
                    │  Agent (非确定性推理客户端) │
                    └─────────────┬─────────────┘
                                  │ 1. 携带期望版本与幂等键
                                  ▼
                    ┌───────────────────────────┐
                    │   CAS 并发控制与版本状态机   │  ← 服务端强校验
                    │  - expected_revision      │
                    │  - idempotency_key        │
                    │  - status: needs_input    │
                    └─────────────┬─────────────┘
                                  │ 2. 状态明确，拒绝脑补
                                  ▼
                    ┌───────────────────────────┐
                    │    真实业务数据与事务执行   │
                    └───────────────────────────┘
```

1. **版本条件写（CAS / Optimistic Concurrency Control）**：
   * 像 Interior 的 `refine_design` 强制要求传入 `expected_revision`。Agent 无论重试多少次，只要版本号不匹配，立即被安全拦截，杜绝脏写。
2. **副作用严格声明（Declarative Side Effects）**：
   * 架构上必须把只读探索（Discovery）、本地自检（Validation）、暂态草稿（Draft）与最终破坏性提交（Commit）严格在边界上切开，消灭“万能执行器”。
3. **把业务过程实体化（Lifecycle Observability）**：
   * 请求到达（ACK 200）不等于业务完成。必须把长任务建模为独立的状态实体（`accepted -> running -> partial -> completed`），允许 Agent 在网络断开后重新连上并查询进度，杜绝“盲目重试导致的重复扣款与采购”。

### 维度四：零信任与“权限-责任”解耦（Authority vs. Execution）

在架构安全层面，Agent-Ready 彻底颠覆了传统的 RBAC（基于角色的访问控制）：

* **拒绝“代理自报信任”**：
  * Agent 传入 `owner_confirmed: true` 绝不能当作真实授权凭证。
* **分权架构：探索权与认领权分离（Draft & Claim Pattern）**：
  * **Agent 拥有“方案探索与编排权”**：可以自由调用模型、调整参数、生成临时 Draft（带有时效性与隔离沙箱）；
  * **人类 Owner 拥有“终局资产与履约权”**：最终的扣费、对外发邮件、正式落库，必须通过人类可信通道（如扫码、网页 Claim、独立签名）完成交接。
  * 这种设计使得 Agent 即使发生幻觉或遭遇 Prompt Injection 攻击，其破坏半径也被严格限制在暂态草稿内。

### 维度五：领域核心与接入协议的解耦（Core Domain vs. Ingress Protocol）

很多团队的架构错误在于：**为了支持 Agent，在代码里四处硬编码 MCP**。

真正的架构师会看到：**MCP、OpenAI Plugins、Claude Tools、A2A 甚至未来的 Code Mode，都只是网关接入层（Ingress / Transport Layer）的协议方言。**

```
               ┌───────────┐    ┌───────────┐    ┌───────────┐
  接入层       │    MCP    │    │   REST    │    │ Code Mode │
 (Ingress)     │ (Claude等)│    │(Web人类端) │    │(受控沙箱)  │
               └─────┬─────┘    └─────┬─────┘    └─────┬─────┘
                     └────────────────┼────────────────┘
                                      ▼
               ┌─────────────────────────────────────────┐
 领域核心      │         Agent-Ready 核心领域内核        │
 (Domain Core) │ - Bounded Intent (高阶业务意图)         │
               │ - Idempotent & Reversible (幂等与可恢复) │
               │ - Provenance & Validation (证据与强校验) │
               └─────────────────────────────────────────┘
```

* **内核做厚，协议做薄**：
  * 业务内核必须本身就具备：有界意图、幂等性、强类型校验、状态机和可追踪凭据；
  * 如果领域内核本身是 Agent-Ready 的，那么外面挂一个 MCP Server 只需写几行适配代码；如果内核还是混乱的页面级 CRUD，套上一百层 MCP 也依然脆弱不堪。

---

### 架构师眼中的一句话总结

> **Agent-Ready 是企业架构的一次“去人脑隐式依赖”重构。**
> 
> 它不是在讨论某个具体的协议，而是**系统如何为“非确定性推理客户端”建立强确定性的契约、状态机、容灾边界与资源防御**，从而让 AI 智能体在脱离人工盯盘的情况下，依然能驱动复杂的真实业务飞轮。
