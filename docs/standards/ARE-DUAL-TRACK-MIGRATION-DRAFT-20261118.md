# ARE 双卷拆分：第三方 MCP 产品卷与使用方治理卷

**2026-11-18 · 供 Claude/Codex/ChatGPT 交叉审核的实施草案，非正式新标准。**

## 决策

原 ARE-A02@0.5 的 39 个检查不能直接用于给第三方 MCP 产品发成熟度等级。它们混合了 MCP 供应商、使用该 MCP 的组织，以及双方共同承担的责任。

- **卷 A / MCP Product & Agent Usability**：只对特定版本/端点/工具范围内 MCP 自身可控制的产品能力进行验证。独立 ARE 评测者可以从黑盒、公开源码、已授权测试环境和真实 Agent 任务取得证据，不得因供应商不能交付某客户组织的价值卡、业务审批、ROI 等给它扣分。
- **卷 B / Adoption & Operations**：只评估采用组织在明确业务场景下的价值、授权、安全使用、上线、运营与复盘。**保留业务上的 L1 Value Defined → L2 Read-Ready → L3 Write-Safe → L4 Verified Operations，但重写不属于采用方责任的门槛。**
- ARE 是独立裁判，不是第三张被考核的卷。协议 MUST/SHOULD、ARE 自定的产品质量标准、实际 Agent 任务结果是分开的证据，不混成一个认证分数。

原 39 项逐项映射存放在 **`data/are-assessment-track-map.v1.json`**；源真值仍是 `data/checks.yaml`。原始 ID、历史评分、公开案例均不可直接改写。映射的状态是 `DRAFT_NOT_SCOREABLE`。

## 第一轮归属：16 个产品专属 / 7 个采用方专属 / 16 个双边拆分

原 39 条并没有直接变成「16+7」。双边项必须分别形成可证伪的检查命题，试拟 **32 条产品原子检查与 23 条采用方原子检查**（总共 55 条待校准的检查原子），它们不是已批准的 55 条强制标准；产品卷的最终合并/缩减取决于后续 10 个 MCP 的真实任务校准。

## 评分与适用性

1. 互斥状态：`PASS`、`FAIL`、`NOT_APPLICABLE`、`UNKNOWN`、`NOT_TESTED`、`BLOCKED_AUTH`。不将 `DESIGN_GAP` 作为可计分状态。
2. `FAIL` 仅当 **事前明确的强制条件**适用于该工具/风险类别，固定版本的实际测试发现可重复不满足，且归因于该被测方。有原始输入、日志、预期、实际与证据链接。强制项不满足不能改叫建议。
3. 非强制建议独立写在 **Non-scored recommendations**；不能被计入分子或分母。协议级 `MUST` 违规须另列官方规范版本和逐条依据，不能把 ARE 偏好的分页、字段形式当成 MCP MUST。
4. `UNKNOWN` 是未知而非失败，`NOT_TESTED` 是本次没有执行，`BLOCKED_AUTH` 是无权测试。负面结论不能基于它们推导。
5. `NOT_APPLICABLE` 要通过操作风险清单提供可复核的非适用理由：纯只读服务不要求撤销写入，短同步服务不要求长任务恢复，小体积常量不要求分页；也不能任意滥用 N/A 把必要条件免掉。
6. 一个第三方产品没有真实使用方的证据时，卷 B 状态为 `NOT_ASSESSED`，**不能误写 L0**。卷 A 的产品等级结构尚待十项目校准，不借用现有 L1–L4 的「价值明确」含义。
7. 两卷都固定 `endpoint`、`observed_version`、`host_adapter`、`test_scope`、`tool_coverage` 和 `evidence_ids`。区分 ChatGPT 工具适配层观察与原生 MCP 服务端源代码的可证事实。

## S0–S13 / W1–W6 发布门禁迁移

新的评估流程要区分：`protocol_conformance`、`mcp_product_assessment`、`agent_task_results`、`enterprise_adoption_maturity`。

- **S7**：新案例创建独立的产品/采用方结果；旧 39 条状态填满仅为历史兼容，不是对产品缺陷或认证的判定。
- **S8 / G3**：验证真实 Agent 调用、独立 Oracle、固定版本、适用性和 FAIL 归因，事实纠错；敏感信息及未公开风险不发布。
- **S10 / G4**：发布前必须有与案例版本一致的可信 QA 和授权收据。仅 Agent 自报的 `public_qa_pass=true`、`approved=true`、`39/39` 不能赋予发布权。
- **W5**：历史已发布的 v1 案例保留；**新的案例在明确新双卷发布协议及可信发布校验器上线前，应停留于草稿/私有开发者反馈，不得沿用 v1 的“39 项齐全”判断自动公开新评价。** 不得借由回填旧日期绕过生产可信的首次创建时间/发布审批记录。
- **版本与回滚**：新旧结果分开，迁移不可改变历史 Solarstorm、Remote Desktop Commander 的原始证据或显示为认证等级；已刊错误只能附带更正声明与版本化历史。

`scripts/are_assessment_tracks.py` 只校验拆分映射、展示原子检查数量与结果证据格式；它不授等级，不发邮件、不发布。必须由真正的 Worker 在未来实现受信任的权限/QA/幂等/发布回执绑定。


## 10 个 MCP 校准前的可执行条件（2026-11-18 预注册草案）

所有 55 项逐条规则在 `data/are-assessment-criteria-pilot.v1.json`；解析及证据归因检查在 `scripts/are_criteria_pilot.py`。已经预先定义每项的 `obligation`（REQUIRED / CONDITIONAL_REQUIRED / RECOMMENDATION）、`applies_when`（机器可判定的事实谓词）、`pass_if`（具体指标/比较符/预定阈值）、`failure_standard`（可证伪失败行为）与证据责任方。

- **产品卷 32 项**：2 项 REQUIRED、29 项 CONDITIONAL_REQUIRED、1 项 RECOMMENDATION。REQUIRED 和适用条件已证实的 CONDITIONAL_REQUIRED **都有可能产生严格 FAIL**，没有 `DESIGN_GAP` 计分状态。
- **采用方卷 23 项**：5 项 REQUIRED、18 项 CONDITIONAL_REQUIRED；只有选定组织/场景后才能评估，外部第三方 MCP 没有组织场景时是 NOT_ASSESSED，而非 L0。
- **试点阈值**：`MCP-L2-X4` 默认只读响应最大 8192 Token（显式指定大型返回值另算）；`MCP-L2-X3` 工具数达到 **25** 才强制要求渐进发现或等效上下文控制。两者是评估前固定的 *校准假设*，非 MCP 规范 MUST，也非已经颁布的 ARE 正式阈值；10 个样本后允许通过有版本记录的修订，不能倒改试点结果。
- **L4-R1**：产品侧改为供应商是否提供 **可授权测试/沙箱入口**，而非难以从公网核实的供应商内部流水线。
- **L4-O2**：供应商内部回归门禁列为外部评价的**不计分建议项**，公开证据或经授权审计仍可记录；缺乏公开证据 ≠ FAIL。只有确实需要且被拒绝的测试权限才记 BLOCKED_AUTH，否则 UNKNOWN/NOT_TESTED。
- **归因门槛**：产品卷以原生 MCP 调用或绑定供应商代码为依据。ChatGPT 适配层单侧观察不能变成供应商 FAIL；无版本、无可查证证据、无适用性来源不能 PASS/FAIL。
- **部署门禁**：生产安全热修 PR #25、#26 已在 `main`，Vercel buildCommand、GitHub 必需状态检查及分支保护以 38 个公开静态/历史案例文件的哈希锁定未经授权的发布；这不是新的评分标准，也不能被 `39/39` 替代。更新历史案例需正式记录修订并审查/重新固定哈希。

**仍是校准草案**：本规则可以产生内部、附证据的单项试点评价，但不可赋予产品成熟度等级，不可作为对外自动发布的授权。

## 十 MCP 真实任务校准实验

先做完双卷拆分与权限/发布隔离，再挑 10 个不同形态的 MCP：小型只读、大型查询、本地文件、需认证只读、普通写入、异步长任务、草稿-提交、外部副作用、多入口、源码与部署可绑定案例。每个尽可能 3 个真实 Agent 任务尝试，日志保留模型/宿主/实际工具调用/独立 Oracle/重试/字节及 Token/延迟/成本；副作用只在明确授权的沙箱中进行。统计每条卷 A 条目的可核验率、误判率、复测稳定性、对 Agent 任务成功的解释力，再决定哪些检查强制、条件适用或仅建议。
