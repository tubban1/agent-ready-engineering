# ARE V5.3：什么能证明，什么还不能证明（2026-11-22）

**ARE 是检查员。Agent 是证人。只有检查员核实过的证据，才可以成为正式结论。**

## 新增的通用规则

1. **不许编造用户拒绝授权。** OAuth 的 RFC 9728 元数据地址是机器描述，不是用户登录/同意页面。Agent 不能凭自己输入的 USER_DECLINED 说明用户拒绝。当前还没有跨 Antigravity / Claude / Codex 通用的、由真实用户或服务商签发的可信授权事件，所以不接受 Agent 自报的用户拒绝。等待真实授权时任务保持未完成。
2. **不许把外部副作用当成已授权。** 注册账户、发送邮件、验证身份、发送邀请或付款等成功调用，没有可信的真人授权凭证时不能获得正式合格报告。返回输入校验错误的负面测试仍可记录。此限制会让部分写入工具暂时无法获得 PASS；这是保守安全措施，不是假称已验收。
3. **任务要真的做完。** 一个 Agent 任务 PASS 至少需要两个不同的真实工具调用，独立 Oracle 应检查最后一步。如果最后一步的 next_action 是 collect_code、wait、browser 等中间状态，就不能宣称完整任务成功。
4. **N/A 必须有语义证据。** readOnlyHint=false 不等于不存在读取功能。不能仅凭工具的安全标记就排除读取类准则。
5. **47项阻塞不是47次实测。** 独立原始调用条数、工具覆盖引用次数、单次网关401推断受阻的工具数应分开展示。

## 已知边界

- 没有可信的宿主/服务商授权事件时，ARE 尚不能独立证明真实用户授权；它会拒绝无证的“用户已拒绝”结论。
- Agent 自己生成的截图、文字、Oracle 来源描述，都不能自动成为第三方可信证据。
- 当前严格规则故意限制了注册/发信/支付等写入流程的自动认证；要全面评测这些项目，未来须接入可信宿主事件回执。
- 历史正式报告保留原样，不能自动重写成新规则通过。
- 从本版起只接受 are.evidence.v5.3 和 are.criteria.v5.3；不默默接受 V5.2。

## 什么时候可以说 ARE 方法有用？

参阅 ARE-METHOD-VALIDITY-EXIT-CRITERIA.md。冻结规则后，用至少60个此前没用于调参的项目、3种Agent、两轮测试和人工独立判定完成盲测。只有达到预先规定的错误率和一致性指标，才在**明确范围内**标为已验证。
