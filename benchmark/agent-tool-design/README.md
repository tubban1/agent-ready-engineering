# P2 — Agent Tool Design Experiment (evidence, not branding)

Date: 2026-11-15. Reproducible experiment of **three tool-interface implementations we constructed**, all operating on the same isolated synthetic ticketing state.

## What was compared
1. **`api-wrapper`** — direct CRUD-like tools with verbose ticket records and separate notification. This is one example of a traditional thin wrapper, not all APIs.
2. **`anthropic-principles`** — purpose-named, compact, task-oriented operations following recommendations in Anthropic's September 2025 article. This is **our illustrative adaptation, NOT Anthropic's product or its benchmark**. It also implements stale-write checks; it does not implement a separate operation-status receipt.
3. **`are-operation-contract`** — bounded inspect, prepare, authorized commit and operation-status tools with a request-bound idempotency key and independently verifiable final state. This is our reference implementation, not proof the public ARE service provides a business write engine.

References: https://www.anthropic.com/research/writing-tools-for-agents ; https://modelcontextprotocol.io/specification/2026-07-28/

## Task bank
| Task | Acceptance oracle |
|---|---|
| T01 Normal resolution | ticket resolved, exactly one notification |
| T02 Ack lost after commit | ticket resolved, exactly one notification **and caller can reconcile status** |
| T03 Stale revision | concurrent update preserved, no notification |
| T04 Missing owner approval | no write or notification |
| T05 Read-only investigation | ticket unchanged, no notification |

Each variant starts with the same fixture and test conditions. The oracle reads the fixture's private state, not the controller's self-reported success.

These numbers provide no statistical evidence of general model efficacy, no ranking of Anthropic products, no independent third-party task improvement, and no comparison to a production integration.

## Full P2 acceptance protocol for actual AI agents
The above is a fixture feasibility stage, not the full cross-model experiment. A valid follow-on experiment needs all:
- Two or more actual LLM models *and* at least two real MCP clients/hosts; record model IDs, client versions and actual tool traces. The separate `mcp/test/client-interop.test.ts` and `stdio-interop.test.ts` now validate the **official SDK** in both protocol eras, which is transport interoperability, not multiple model evaluations.
- 20+ realistically composed tasks with a held-out set, multiple independent executions per task, identical fixture hashes and user goals for each variant.
- Independent end-state and side-effect oracle; exact bytes and **measured** tokens only when available from the host; latency with start/end timestamps and environment.
- Safe consented failure injection on isolated synthetic systems; stop on any unapproved write.
- Private review of findings and fixes; a real world maintainer case after explicit opt-in.

### Interpreting results
An interface that creates more tools can reduce task calls but enlarge its tool catalog. A simpler, task-oriented tool might be a better choice for read-only investigations. ARE's additional prepare/confirm/status steps add overhead, but they are designed to preserve business authority and recoverability after ambiguous writes. Do not declare a general 'winner'; choose according to real task risks and verified user outcomes.

P2 report must keep **MCP spec conformance**, **ARE L0-L4 maturity**, and **actual agent task success** as three distinct evidence lines.
